Your question

Will a migration dashboard on the Projects page add value?

Yes. It is the most useful addition in this proposal, because today nothing in the app answers “how far along is our migration?” Project cards show only name, source, target, tags and status. A sponsor or team lead has to open every run report to add it up.

Put it above the list, not below. Below the list, nobody scrolls to it once there are 20+ projects. Keep it to one band of 4 numbers plus one “needs attention” row, and let people collapse it. The full breakdown can live on each project's Overview tab.

Most of the data already exists. Each run's report summary (/api/projects/:id/runs/:run/report-summary) returns tables, columns, measures, relationships, and counts of items converted cleanly, converted with AI help, needing review, dropped and excluded. What's missing is one endpoint that adds up the latest run of every project, and tracking for Ask AI usage.

Duplicates are found by comparing normalised formulas, not just names. Exact matches can be merged in one click; near matches need a person.
Conflicts use the existing collision check against domains already in the ontology, so a new project can't quietly redefine a certified metric.
Glossary gaps are filled with AI drafts that a person accepts or edits. Accepted text goes to the target as column and metric comments.
Skippable, but tracked. “Skip for now” creates the project with an ontology score of “Not reviewed”, shown on the Projects list.

What this changes in the flow. Today the dry run converts every measure it finds, so 3 copies of Revenue become 3 Snowflake metrics, and the ontology is generated afterwards from the result. With this step:

Choose models → read models (quick parse, no target calls) → Ontology review → dry run against the target using the merged list → Review → create. The dry run converts fewer measures, uses less AI, and the target gets one name per business metric with descriptions attached.

One technical dependency: the step needs the source models parsed before the dry run. If parsing currently happens only inside the dry-run job, it needs to be split out as its own fast call. The existing /ontology/domains/from-osi endpoint can then build the draft from that parsed model.

Build order

How to roll it out

The order puts the most visible value first, and each step ships on its own.

  1. Shell and renames. New sidebar groups, top bar without the status bar or Version Control icon, route redirects (/jobs→/runs, /explore→/map, /version-control→/history). Delete the unused components/Header.jsx and components/LoginPage.jsx.
  2. Projects summary. Add GET /api/projects/summary, which totals the latest run report summary for each project, and the summary band and table view on Projects. This answers the dashboard question.
  3. Ontology step in the wizard. Split source parsing out of the dry-run job, add formula-based duplicate detection and a glossary coverage score next to the existing collision check, and insert the Ontology step before Check. The same score feeds the Ontology column on Projects.
  4. One project page. Merge ProjectDetailPage and ProjectConfigPage into tabs. Add the Overview with last-run breakdown and the needs-review list.
  5. Ontology split and Ask AI page, as in the Ontology proposal. Add usage logging for questions so the Projects band can show Ask AI numbers.
  6. Runs drawer and schedules in plain language.
  7. History, Model map, Compare and Settings clean-ups: fewer tabs and fewer toolbar buttons, with the AI model list and YAML editor moved to Settings.
  8. Wizard step 4 becomes the readiness summary, with the grid behind a link.
